# Автопостер відключень — Київська область

Node.js-бот для автоматичного ведення Telegram-каналу. Регіон за замовчуванням — **`kyiv-region` (Київська область)**; `kyiv` — окремий регіон міста Києва.

Потрібен **Node.js 20.12+**, рекомендовано Node.js 24 LTS. Використовуються лише вбудовані модулі: `fetch`, `FormData`, `Blob`, `crypto`, файловий API та тестовий runner. Перевірте `node --version`: Node.js 18 для запуску не підходить.

## Upstash Redis замість state.json

Якщо в `.env` або Environment на Render задані **обидві** змінні нижче, бот автоматично зберігає стан у Redis:

```env
UPSTASH_REDIS_REST_URL=https://your-database.upstash.io
UPSTASH_REDIS_REST_TOKEN=your_read_write_token
```

Скопіюйте REST URL і **Token** з консолі своєї бази Upstash. Read-Only Token не підходить: потрібні `GET`, `SET`, `EVAL`, `PEXPIRE`, `EXPIRE`, `DEL`. URL — звичайний HTTPS рядок без Markdown-дужок, зайвого шляху та зворотного слеша. Токени не додавайте до Git і не надсилайте в чат.

Перевірка реального підключення без Telegram-публікацій:

```sh
node index.js --check-redis
```

Команда перевіряє lock, атомарний запис і читання на унікальному тимчасовому ключі. Він зникає через 5 хвилин; робочий стан не змінюється. `403` за успішного PING означає, що токен не має права на потрібні команди.

Якщо вже є робочий `state.json`, **зупиніть попередній бот**, залиште той самий `REGION` і `TELEGRAM_CHAT_ID`, та перенесіть стан перед запуском Redis-версії:

```sh
node index.js --migrate-state
```

Міграція зберігає локальний файл і не перезаписує вже наявний стан Redis. Файловий lock не дозволить перенести state, поки старий локальний процес працює. ID каналу має точно збігатися зі старим state: числовий ID та `@username` одного каналу автоматично не ототожнюються. Коли локальної історії немає, міграція не потрібна — створюється baseline при першому звичайному запуску.

У Redis зберігається весь стан: графік, sent IDs, хеші PNG, pending urgent та cooldown. Ключ залежить від регіону й каналу; робочий state не має TTL. Використовуйте базу без автоматичного витіснення цих ключів. Після втрати/видалення ключа бот не зможе відновити історію відправлень.

Redis lock має унікальний token власника і TTL 180 секунд, поновлюється щохвилини та перед кожною спробою Telegram API. Lua атомарно перевіряє власника при записі й звільненні lock. Другий процес не запускає публікації. Після аварійного завершення новому процесу інколи потрібно зачекати до 3 хвилин, поки старий lock закінчиться. При втраті доступу чи lock процес зупиняє нові публікації та завершується з помилкою; автоматичного переходу на локальний файл немає. PM2/Render/systemd може його перезапустити. Межа exactly-once Telegram, описана нижче, залишається.

Без обох змінних бот продовжує використовувати локальний `STATE_FILE`; якщо задана лише одна, запуск завершується помилкою конфігурації.

На Render використовуйте **Background Worker**, build `npm ci`, start `node index.js`, один екземпляр, Node.js 24. У Environment додайте Telegram, REGION і обидві Upstash-змінні. **Persistent Disk та STATE_FILE для Redis-режиму не потрібні.** Redis не вирішує засинання безкоштовного Web Service; для постійного polling потрібен постійно активний процес.

## Швидкий запуск

1. У Telegram відкрийте [@BotFather](https://t.me/BotFather), виконайте `/newbot`, задайте назву та username, збережіть виданий токен.
2. Додайте бота до адміністраторів потрібного каналу з правом публікувати повідомлення.
3. Визначте числовий ID каналу способом нижче.
4. У каталозі проєкту виконайте:

```sh
npm install
```

5. Скопіюйте `.env.example` у `.env` (`Copy-Item .env.example .env` у PowerShell або `cp .env.example .env` у Linux). Заповніть `TELEGRAM_BOT_TOKEN` та `TELEGRAM_CHAT_ID`. Залиште `REGION=kyiv-region`.
6. Перевірте й запустіть:

```sh
npm run check
npm test
npm start
```

Перший запуск створює baseline без картинки. Попередження про близькі події вже працюють. Для публікації картинки на першому запуску встановіть `POST_ON_FIRST_RUN=true` **до створення state**. Цей параметр не змушує повторювати картинку після кожного restart.

## Як отримати TELEGRAM_CHAT_ID

Після додавання бота опублікуйте в каналі новий допис вручну. Збережіть токен у `.env`, а потім виконайте локально:

```sh
node --env-file=.env --input-type=module -e "const r=await fetch('https://api.telegram.org/bot'+process.env.TELEGRAM_BOT_TOKEN+'/getUpdates?allowed_updates=%5B%22channel_post%22%5D');const j=await r.json();if(!j.ok)throw Error(j.description);console.log(j.result.map(x=>x.channel_post?.chat).filter(Boolean));"
```

Візьміть `id` відповідного каналу, наприклад `-1001234567890`. Токен команда не друкує. Якщо результат порожній, опублікуйте ще один допис і повторіть. `getUpdates` не працює за наявності webhook; для цього автопостера найпростіше створити окремого бота, який не використовується іншими застосунками. Для публічного каналу також можна отримати `id` методом `getChat`, передавши його `@username`. Документація: [getUpdates](https://core.telegram.org/bots/api#getupdates), [getChat](https://core.telegram.org/bots/api#getchat).

Сам автопостер не читає вхідні повідомлення й не використовує webhook.

## Конфігурація

| Змінна | Значення за замовчуванням | Призначення |
| --- | --- | --- |
| `TELEGRAM_BOT_TOKEN` | обов'язкова | Токен BotFather |
| `TELEGRAM_CHAT_ID` | обов'язкова | Числовий ID `-100…` або публічний username `@bc_light` |
| `REGION` | `kyiv-region` | Ім'я JSON у `data/` |
| `CHECK_INTERVAL_SECONDS` | `60` | Перевірка кожні 1–3600 секунд |
| `NOTIFY_BEFORE_MINUTES` | `30` | Попередження за 1–1440 хвилин |
| `POST_ON_FIRST_RUN` | `false` | Картинка при створенні baseline |
| `HTTP_TIMEOUT_SECONDS` | `20` | Timeout одного запиту, включно з тілом відповіді |
| `RETRY_ATTEMPTS` | `4` | Максимальна кількість спроб одного запиту |
| `RETRY_BASE_MS` | `1000` | Початкова затримка exponential backoff з jitter |
| `STATE_FILE` | `./state.json` | Шлях до постійного стану |
| `UPSTASH_REDIS_REST_URL` | порожня | HTTPS endpoint Upstash; разом із токеном вмикає Redis |
| `UPSTASH_REDIS_REST_TOKEN` | порожня | Токен із правами читання й запису |

Щоб змінити 30 хвилин, задайте `NOTIFY_BEFORE_MINUTES` і перезапустіть процес. Для своєчасних повідомлень бажано залишити polling 60 секунд. Запускайте з каталогу проєкту: `.env` і відносний `STATE_FILE` шукаються від поточного каталогу.

Для іншого регіону змініть `REGION`, перевірте `npm run inspect` та використайте **окремий `STATE_FILE`**. Регіон повинен мати ту саму перевірену структуру й загальні PNG; при несумісній схемі бот відмовиться публікувати. Один процес обслуговує один регіон/канал; кілька процесів можуть працювати з різними файлами стану.

## Реальна структура джерела

Досліджено [outage-data-ua](https://github.com/Baskerville42/outage-data-ua), commit `990e587523b0ca057bcfafe1fa9c24da4af90666`, 6 жовтня 2026. Копія реального JSON збережена у `test/fixtures/kyiv-region.json`. Робочий бот читає RAW `main`, а не fixture і не GitHub API.

Джерела дослідження:

- [JSON Київської області](https://github.com/Baskerville42/outage-data-ua/blob/990e587523b0ca057bcfafe1fa9c24da4af90666/data/kyiv-region.json).
- [Генерація загальних PNG](https://github.com/Baskerville42/outage-data-ua/blob/990e587523b0ca057bcfafe1fa9c24da4af90666/scripts/batch_render.mjs).
- [HTML renderer та вибір дня](https://github.com/Baskerville42/outage-data-ua/blob/990e587523b0ca057bcfafe1fa9c24da4af90666/templates/html/schedule-shared.js).
- [Обчислення upstream contentHash](https://github.com/Baskerville42/outage-data-ua/blob/990e587523b0ca057bcfafe1fa9c24da4af90666/scripts/parse_fact.js).

`fact.data` має вигляд `{ UNIX_SECONDS: { GPV1.1: { "1": "yes", ... }, ... } }`. Ключ дня — Unix timestamp опівночі Kyiv. `fact.today` визначає день для `gpv-all-today.png`. `preset.time_zone` задає слоти: `"1": ["00-01", "00:00", "01:00"]`, …, `"24": ["23-24", "23:00", "24:00"]`. Групи беруться з фактичних даних без фіксованого списку.

`preset.data` — тижневий шаблон; його не підставляємо замість відсутніх фактичних даних. `preset.time_type` пояснює семантику:

| Стан | Перша половина години | Друга половина |
| --- | --- | --- |
| `yes` | ON | ON |
| `no` | OFF | OFF |
| `first` | OFF | ON |
| `second` | ON | OFF |
| `maybe` | MAYBE | MAYBE |
| `mfirst` | MAYBE | ON |
| `msecond` | ON | MAYBE |

Інших станів у досліджених даних не виявлено. Сам upstream renderer місцями відображає `mfirst/msecond` як звичайні половинні відключення; текстові попередження цього бота зберігають невизначеність згідно з `preset.time_type`. Завершення MAYBE називається завершенням періоду можливих відключень, а не гарантованим увімкненням.

`fact.updateFact` у дослідженому JSON — `null`, `fact.update` — `06.10.2026 12:16`; в caption береться перше непорожнє з цих полів. `lastUpdated` — технічний час збору. `lastUpdateStatus.ok` має бути `true`; при `false`, відсутньому статусі, неповних слотах або невідомому стані цикл відхиляється, попередній валідний state зберігається. Невідомі поля ігноруються; невідомі назви груп логуються та пропускаються. Порожній день завтра не вважається днем із живленням.

`meta.contentHash` upstream обчислює з вихідного тексту `fact + preset`; він може змінюватися через timestamps, тижневий шаблон або форматування. Бот обчислює власний SHA-256 від відсортованих фактичних дат, груп і півгодинних станів. Зміни технічних полів не викликають публікації.

Загальні картинки: **`images/kyiv-region/gpv-all-today.png`** і **`gpv-all-tomorrow.png`**. `gpv-1-1-summary.png` — лише одна група. Tomorrow публікується тільки за наявності відповідного наступного дня в JSON: upstream може залишити там копію today, коли завтра ще не опубліковано. Бот публікує лише змінені актуальні дні, без повтору незмінної картинки сьогодні через зміну завтра.

Готовий PNG завантажується у Buffer, перевіряється сигнатура та надсилається multipart upload через [sendPhoto](https://core.telegram.org/bots/api#sendphoto). Власна картинка не генерується. Параметри URL обходять звичайне кешування, а повторне читання JSON після PNG виявляє зміну джерела під час завантаження. Upstream workflow комітить JSON і PNG разом. При цьому RAW/CDN не надає криптографічного зв'язку PNG з JSON: перевірка узгодженості захищає від видимої гонки оновлення, але не доводить свіжість кожного пікселя.

## Monitoring, порядок публікацій і стан

`index.js` містить окремі компоненти `normalize`, `transitions`, `Monitor`, `Transport`, `StateStore`. Кожен цикл завантажує свіжий JSON, перевіряє схему, будує півгодинний timeline і знаходить переходи. Час, логи й дати використовують `Europe/Kyiv`, включно з 23/25-годинними днями переходу на літній/зимовий час. На початку дня без попереднього відомого слота перехід не вигадується; між двома суміжними днями перехід о 00:00 враховується.

При зміні графіка спочатку зберігається новий стан і намір термінового повідомлення, потім публікуються змінені PNG, потім текст. Якщо PNG недоступний, текст цього циклу чекає успішної публікації PNG. Намір зберігається після restart. Зміни часу автоматично замінюють майбутні події; багатогодинних `setTimeout` немає.

Вікно повідомлення: `0 < eventTime - now <= NOTIFY_BEFORE_MINUTES`. Це дозволяє наздогнати polling після короткого збою. Текст показує фактично залишені хвилини. Після початку події нові спроби не запускаються. Якщо новий перехід уперше з'явився в оновленому графіку ближче за налаштований інтервал, повідомлення термінове. На першому baseline пізнє повідомлення звичайне, бо немає попереднього графіка для порівняння.

Усі нові переходи одного моменту об'єднуються в одне повідомлення: OFF, ON, MAYBE та завершення MAYBE мають окремі секції. ID відправлення — `epochMilliseconds|kind|group`. Коли додали групу, повторно надсилається лише нова група. Скасовані повідомлення бот не видаляє; новий PNG відображає актуальний графік.

`state.json` містить normalized schedule, хеші вже опублікованих картинок за датами, sent IDs, pending urgent IDs та Telegram cooldown. Sent IDs очищаються через 3 дні від часу події. Запис: унікальний тимчасовий файл → `fsync` → atomic rename. На Linux також виконується `fsync` каталогу. State з іншого каналу/регіону або пошкоджений JSON спричиняє зрозумілу помилку запуску, а не тихе скидання dedup.

Файл `.lock` забороняє два процеси з одним state. Після аварії lock із PID відсутнього процесу прибирається автоматично; некоректний lock потребує ручної перевірки. SIGINT/SIGTERM завершують поточну обмежену timeout операцію та звільняють lock. Критична помилка запису state завершує процес, щоб не продовжувати публікації без dedup.

HTTP 5xx, network timeout та invalid JSON повторюються з backoff. Telegram 429 враховує `retry_after`; тривале очікування переноситься в наступні цикли зі збереженим cooldown. Неуспішне відправлення не позначається `sent`. При недоступному/некоректному джерелі старий графік залишається на диску, але нові попередження за неперевіреними даними не надсилаються.

**Межа гарантії dedup:** звичайний restart після підтвердженого й записаного відправлення не створює дубля. Telegram Bot API не має idempotency key для цих методів: якщо Telegram прийняв запит, але відповідь загубилася, або процес аварійно завершився між успішною відповіддю і записом state, retry може створити дублікат. Повністю гарантувати exactly-once у цьому проміжку неможливо; це стосується як тексту, так і PNG.

## Перевірки

```sh
npm run check
npm test
npm run inspect
node index.js --inspect-schedule --file test/fixtures/kyiv-region.json
```

`inspect` читає актуальний RAW JSON і друкує переходи; токен не потрібен, публікацій та запису state немає. Тести використовують знімок реального JSON, контрольований час, тимчасові state-файли й локальний HTTP-сервер для 500/timeout/invalid JSON/429. Telegram-відправлення симулюються тільки в тестах. Окремо перевіряється multipart PNG upload, половинні стани, агрегація, dedup після restart, термінова зміна за 5 хвилин та порядок PNG → текст.

У знімку на **6 жовтня 2026** знайдено 12 груп, 10 переходів, 5 моментів:

| Час Kyiv | Перехід | Групи |
| --- | --- | --- |
| 15:00 | OFF | 5.1, 5.2 |
| 17:00 | OFF | 1.1, 1.2 |
| 17:30 | ON | 5.1, 5.2 |
| 20:00 | OFF | 3.1, 3.2 |
| 20:30 | ON | 1.1, 1.2 |

Це результат розбору знімка, а не гарантія актуального графіка надалі. Завтра у цьому знімку ще відсутнє.

## Робота 24/7 через PM2

Потрібен комп'ютер або сервер без режиму сну, з постійною мережею. Приклад для Linux:

```sh
npm install -g pm2
pm2 start index.js --name kyiv-region-outages --kill-timeout 300000
pm2 save
pm2 startup
```

Виконайте команду встановлення автозапуску, яку надрукує `pm2 startup`. Перегляд: `pm2 logs kyiv-region-outages`; після зміни `.env`: `pm2 restart kyiv-region-outages`. Запускайте один екземпляр, без cluster mode. PM2 на Windows можна використовувати для перезапуску процесу, але автозапуск Windows налаштовується окремо через Планувальник завдань. [Документація PM2](https://pm2.keymetrics.io/docs/usage/quick-start/).

## Альтернатива: systemd

Припустімо, код, `.env` і початковий робочий каталог розміщені в `/opt/kyiv-outage-bot`, створено системного користувача `outagebot`, а Node.js 20.12+ встановлено в `/usr/bin/node`. Власником каталогу має бути `outagebot`, щоб він міг створити state і lock. Файл `/etc/systemd/system/kyiv-outage-bot.service`:

```ini
[Unit]
Description=Kyiv region outage Telegram autoposter
Wants=network-online.target
After=network-online.target

[Service]
Type=simple
User=outagebot
Group=outagebot
WorkingDirectory=/opt/kyiv-outage-bot
ExecStart=/usr/bin/node /opt/kyiv-outage-bot/index.js
Restart=on-failure
RestartSec=10
TimeoutStopSec=300
KillSignal=SIGTERM
UMask=0077
NoNewPrivileges=true
PrivateTmp=true

[Install]
WantedBy=multi-user.target
```

```sh
sudo systemctl daemon-reload
sudo systemctl enable --now kyiv-outage-bot
sudo journalctl -u kyiv-outage-bot -f
```

Виберіть один менеджер процесу: PM2 або systemd. State повинен лежати на постійному локальному диску і зберігатися при оновленні коду. Після зміни регіону/каналу створюйте новий state, не підмінюйте поля старого вручну.
